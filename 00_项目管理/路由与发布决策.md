# 路由与发布决策：一篇文章从入库到发出，到底谁说了算

> 整理于 2026-10-17，依据当时的代码与生产库实测。
> 改动相关逻辑前请先读完本文，尤其是第六节「容易看混的地方」。

## 这份文档解决什么问题

「栏目」「来源」「赛事规则」三套配置叠在一起，加上 AI 护栏，很难一眼看出某篇文章
为什么挂在这个栏目、为什么是直发而不是草稿。本文把判定顺序完整拆开，并标注代码位置。

---

## 一、先分清两个决策

这是最关键的一点：**有两个互相独立的决策，在两个不同的时间点做出。**

| | 决策 A | 决策 B |
|---|---|---|
| 问题 | 这篇**挂哪个栏目** | 这篇**怎么发**（草稿 / 直发 / 放弃） |
| 时间 | 入库那一刻 | 发布那一刻（通常晚几分钟到几小时） |
| 落库 | `article_tabs` + `articles.route_*` | `articles.publish_mode` |
| 可变性 | **快照，此后不随配置变化** | **快照，一旦写死不再重算** |

两个决策共用了名字几乎一样的配置字段（见第五节对照表），这是混淆的主要来源。

## 二、第一层：入库时定栏目

代码：`repository.upsert_material()` → `repository._resolve_material_tabs()`
（`app/repository.py:1320` / `app/repository.py:1198`）

### 2.1 唯一输入：`user_name`

素材接口返回的 `material_user_name`，格式 `媒体:运动.联赛.球队`，例如
`nikkan:soccer.intl.xxx`。由 `parse_material_user_name()`（`app/repository.py:233`）解析。

- `_` / `xxx` / 空 一律归一化成空字符串
- 格式不合法（没有 `:`、点分段不是 3 段）整条作废，league/team 都为空

> `articles.route_league` 为空 ≠ 出错，它的意思是「上游没给联赛信息」。

### 2.2 规则匹配顺序

```
先用 team 标记查 event_tab_rules ──┐
                                   ├─ 先命中的赢（team 优先于 league）
再用 league 标记查 ────────────────┘

每次查找内部还有一层优先级（_find_event_tab_rule, app/repository.py:1177）：
    source_code = 本来源的专属规则   >   source_code IS NULL 的通用规则
    同级再按 r.id 升序取第一条

且规则必须满足：
    r.enabled = 1
    且（绑定的栏目存在且 tabs.enabled = 1   或   r.publish_mode_override = 2）
```

注意最后一条：**规则指向一个已停用的栏目时，这条规则视同不存在**，文章会退回按来源路由。
放弃规则（override=2）是例外，它不需要绑栏目。

### 2.3 三种结局

| 结局 | 栏目怎么定 | `route_match_type` | 后续 |
|---|---|---|---|
| 没命中任何规则 | = 该来源配置的**全部**栏目（`source_tabs`） | `source` | 正常走质检 |
| 命中普通规则 | = 来源栏目里的「精选(58)」**＋规则指定的那一个栏目**。来源自带的其他赛事栏目**全部被替换掉** | `league` / `team` | 正常走质检 |
| 命中放弃规则（override=2） | = 来源的全部栏目（照挂不动） | `league` / `team` | **立即 `ABANDONED`**，同时写死 `publish_mode=2`，不质检、不发布 |

「精选(58)」是唯一的通用来源栏目，只在来源本来就配了它时才保留
（`GENERIC_SOURCE_BACKEND_TAB_ID`，`app/repository.py:1543`）。

> **实例**：韩媒来源默认栏目是「韩K」，某篇 league 标记是 `epl`，命中通用规则
> 「epl → 放弃」。于是文章挂在「韩K」栏目下、状态直接 ABANDONED、内容其实是英超。
> 近 30 天这样的文章有 4484 篇。看统计时按栏目聚合会显得「韩K 大量放弃」，
> 实际和韩K 无关。

### 2.4 这一层的产出

写入 `articles` 的：`tab_id`、`route_league`、`route_team`、`route_match_type`、
`route_rule_id`；写入 `article_tabs` 的：选中的栏目集合。

**此后再改来源配置或赛事规则，都不会影响已入库的文章。** 只有 AI 护栏（第四层）
能改栏目。

## 三、第二层：质检

代码：`pipeline._process_article()`（`app/services/pipeline.py:784`）→ `quality.evaluate()`

只看内容本身的质量：标题完整性、正文完整性、广告、脏内容、地域敏感词、
非中文比例等。必要时做高置信局部修复 + 二次完整质检。

**这一层完全不判断「文章和栏目相不相关」。**

产出：`READY_TO_PUBLISH`（进待发队列）或 `NEEDS_REVIEW`（人工）。

## 四、第三层：发布时定模式

代码：`publisher.publish_ready_articles()`（`app/services/publisher.py:1598`）

```
1. 标题查重       _title_dedup_gate        → 命中则 TITLE_DUPLICATE，结束
2. 抢占           transition → PUBLISHING   （抢占必须在调 LLM 之前，防两个 worker 各判一次）
3. 算发布模式     _resolve_publish_mode    ← 4.1
4. AI 栏目护栏    _apply_ai_league_guard   ← 4.2（可能改模式，也可能改栏目）
5. 非中文降级     _apply_language_publish_guard
                  正文非中文 > 60% 且算出直发 → 降为草稿
6. 落快照 → 提交懂球帝开放平台
```

### 4.1 发布模式的优先级

`repository.resolve_article_publish_mode()`（`app/repository.py:1683`），高 → 低，命中即止：

```
①  articles.publish_mode 快照非空         → 直接用，②③④ 全不看
②  event_tab_rules.publish_mode_override   (0/1/2)
③  sources.publish_mode_override           (0/1)
④  栏目投票：文章挂的所有「启用且可发布」栏目的 tabs.publish_mode
       全部一致 → 用它
       不一致   → 抛 PublishModeConflict → MAPPING_BLOCKED
⑤  兜底 0（草稿）
```

算完后有一道**强制闸门**：

> 文章只要挂着任何一个**已停用**栏目，且上面算出 1 → **强制压回 0**。
> 理由：不能往一个关掉的栏目里直发。放弃（2）不受此影响。

参与投票的栏目先经过 `is_publishable_tab()` 过滤，排除
`NON_PUBLISHABLE_BACKEND_TAB_IDS = {58 精选, 12 法甲}`（`app/repository.py:1551`）——
这两个栏目永远不会作为提交目标，也不参与投票。

> ⚠️ **`sources.publish_mode` 不参与这个判定**，只有 `sources.publish_mode_override` 参与。
> 前者只剩一条历史路径在用（`_legacy_mode_for_existing_archive`，处理已存在懂球帝文章的兜底）。
> 生产库 30 个启用来源的 `publish_mode` 全是 0，真正起作用的是 `override`。

> 补充：②读的是 `route_rule_id` 指向的**当前**规则（要求 `enabled=1 AND tab_id IS NOT NULL`），
> 不是入库时的快照。但一旦 ① 的快照写死，后面全都不再重算。

### 4.2 AI 栏目护栏的触发条件

`publisher._apply_ai_league_guard()`（`app/services/publisher.py:374`）。
三道闸，全过才真正调用 LLM：

```
闸1  算出来的 mode != 0                                    → 跳过
闸2  route_league 非空 且 该路由规则没开 ai_guard_enabled   → 跳过
闸3  文章挂的栏目里没有任何一个开了 ai_league_guard_enabled → 跳过
```

通过后的流程：

```
check_league_membership(标题, 正文, 栏目名, 栏目定义)   # quality.py:1198
   │
   ├─ belongs=true 且 confidence ≥ league_guard_min_confidence(默认0.9)
   │      → 升级为直接发布
   │
   └─ 否则，分类器模式（league_guard_classifier_enabled，默认开）
          classify_article_tab(...)                     # quality.py:1257
          候选 = list_guard_candidate_tabs()：所有填了 ai_league_guard_definition
                 的栏目（含已停用的，排除精选）           # repository.py:1633
             │
             ├─ 选中某栏目且置信度够 → 改挂该栏目（reassign_article_event_tab）
             │     发布模式按 league_guard_reassign_publish_mode：
             │        always_direct（默认）→ 直发
             │        target             → 沿用目标栏目自己的 publish_mode
             │     但目标栏目若已停用 → 强制草稿
             │
             └─ 选不出 / 置信度不足 / 调用失败 → 维持草稿（fail closed）
```

改挂只动 `article_tabs` 里的赛事栏目（保留精选），**不动 `channels`**——
那是内容标签，不是栏目，两回事。

判定全过程记录在 `quality_json.league_guard`，升级时额外写一条
`LEAGUE_GUARD_UPGRADED` 事件。其中 `actual_competition` 字段是模型报出的
「这篇真正属于哪个赛事」，不受候选栏目限制，聚合它可以看出该新建哪些栏目。

## 五、三套配置各管什么（对照表）

| 配置 | 管栏目（决策A） | 管模式（决策B） | 管 AI 护栏 |
|---|:---:|:---:|:---:|
| `sources` ← `source_tabs` | ✅ 没命中规则时的默认栏目 | — | — |
| `sources.publish_mode_override` | — | ✅ 优先级 ③ | — |
| `sources.publish_mode` | — | ❌ **实际不参与** | — |
| `event_tab_rules.tab_id` | ✅ 命中时替换栏目 | — | — |
| `event_tab_rules.publish_mode_override` | ✅ =2 时入库即放弃 | ✅ 优先级 ②（最高） | — |
| `event_tab_rules.ai_guard_enabled` | — | — | ✅ 闸2 |

## 六、容易看混的地方

1. **`publish_mode` 这个名字出现在 4 张表里**，取值范围还不一样：
   `tabs`/`sources` 是 0/1，`event_tab_rules` 是 0/1/2，`articles` 快照是 0/1/2。
2. **栏目（tab）同时参与两个决策**：决定挂哪、给模式投票、还能强制压回草稿。
3. **`sources` 有两个发布模式字段**，其中 `publish_mode` 已经退役但没删。
4. **AI 护栏的触发条件依赖前两层的结果**（`route_league` 是否为空、mode 是否为 0），
   所以它看起来「时灵时不灵」。其实是确定的，只是条件分散在三个地方。
5. **按栏目做统计会误导**：放弃规则保留来源栏目，所以「某栏目大量 ABANDONED」
   通常和那个栏目无关；改挂成功的文章算在目标栏目名下，原栏目要看
   `quality_json.league_guard.guard_tab_name`。

## 七、2026-10-17 生产库实测快照

近 30 天（`instance/automatic_post.sqlite3`）：

- 入库 33019 篇，日均约 1100
- 到达发布环节 23095 篇：
  - **13679 篇（59%）走 league 标记路径 → AI 护栏被闸1/闸2 完全跳过**
  - 9416 篇（41%）走 source 路径 → 护栏正常运行
- 全库 47 条启用规则，`ai_guard_enabled = 1` 的有 **0 条**
- 护栏实际跑过 9498 篇，其中 **4845 篇（51%）被判不属于原栏目并改挂**
  - 日职联 判不属于 4573 / 属于 375（拒绝率 92%）
  - 韩K   判不属于 2550 / 属于 73 （拒绝率 97%）
  - 巴甲   判不属于 619 / 属于 858（拒绝率 42%）
- 单个 league 标记到发布环节的量：`intl` 6426 居首，是第二名 `kleague1`（3174）的两倍

`actual_competition` 分布 top：国家队 1295、亚运会 690、欧国联 667、国际友谊赛 548、
非赛事 480、英超 413、西甲 327、德甲 186、欧冠 157。

> 前半段（亚运会/欧国联/国际友谊赛/麒麟杯）本来就该进国家队，说明宽口径定义是对的；
> 后半段（英超/西甲/德甲）才是真正该被拦下的。

### 由此暴露的问题

`intl` 是 catch-all 标记，上游自己也说不清内容是什么，却被规则硬挂到「国家队」+ 直发：

```
intl → 闸2 需要 ai_guard_enabled（=0）→ 跳过
     → 闸1 需要 mode=0，而规则 override=1 → 跳过
     → 直发，全程没有任何一步看过文章内容讲什么
```

抽样 40 篇 `intl → 国家队` 已发布文章，可见「瓜帅：始终支持曼城」「踢球者：穆勒助温哥华领跑」
「国米为马佐拉举行悼念仪式」等纯俱乐部内容。而「国家队」栏目的
`ai_league_guard_definition` 第 2、4 条本来就明确排除这类文章——**定义是对的，只是没跑。**

## 八、排查指引

| 现象 | 先看哪里 |
|---|---|
| 文章挂错栏目 | `articles.route_match_type`：`source` 说明上游没给标记、走的来源默认栏目；`league`/`team` 则看 `route_rule_id` 对应的规则 |
| 该直发却成了草稿 | 按 4.1 优先级逐级查；再看是否挂了停用栏目（强制闸门）；再看 `quality_json.league_guard` 和 `language_check` |
| 该草稿却直发了 | 查 `event_tab_rules.publish_mode_override`（优先级最高）；注意 `articles.publish_mode` 快照一旦写死就不再重算 |
| AI 护栏没跑 | 按 4.2 三道闸逐个对；`quality_json` 里没有 `league_guard` 键就是被闸住了 |
| 某栏目大量 ABANDONED | 多半是放弃规则保留了来源栏目，看 `route_league` 到底是什么 |
| 标签（channels）不对 | 与本文无关，见 `app/services/channel_filter.py` 和 `competition_tags.py` |
