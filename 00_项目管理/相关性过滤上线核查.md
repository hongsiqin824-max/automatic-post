## 一、改动概述

此次上线两个功能，都默认开启、无需手动干预：

| 功能 | 环境变量 | 生效范围 |
|---|---|---|
| **相关性过滤** | `AUTOMATIC_POST_RELEVANCE_GUARD_ENABLED=true` | `intl` 路径直发稿（`route_league=intl` + `publish_mode=1`），发布前补跑 AI 归属校验；判「谁都不属于」且高置信(≥0.9) 时降级草稿 |
| **栏目标签白名单** | `AUTOMATIC_POST_COMPETITION_TAGS_ENABLED=true` | 已启用联赛栏目（韩K/日职联/巴甲/德乙/挪超/瑞典超/欧联/澳超/美职联/日职乙/亚冠精英），提交懂球帝前 channels 收敛到本联赛范围 |

其他路径完全不触发。LLM 不可用 / 分类器不确定性会 **fail-open（放行）**，不因缺数据误拦。

### A. 降级效果（核心指标）

#### A1 — 降级事件日均量

```sql
SELECT DATE(created_at) AS d, COUNT(*) AS n
FROM article_events
WHERE event_type='RELEVANCE_DOWNGRADED'
  AND created_at>=date('now','-14 days')
GROUP BY d ORDER BY d;
```

> **怎么看**：日均 0 → StarRocks 凭据没配或 LLM 不通，此功能没跑起来。
> 日均 <5 篇 → intl 路径本来就很干净，正常。
> 日均 5~25 篇 → 拦截正常，编辑在后台能看到这些降级草稿。
> 日均 >40 篇 → intl 路径脏度高于预期，考虑调低 `relevance_guard_min_confidence`（当前 0.9）多看一些。

#### A2 — 降级文章的 actual_competition 分布

```sql
SELECT json_extract(payload_json,'$.actual_competition') AS comp, COUNT(*) n
FROM article_events
WHERE event_type='RELEVANCE_DOWNGRADED'
  AND created_at>=date('now','-14 days')
GROUP BY comp ORDER BY n DESC LIMIT 20;
```

> **怎么看**：每个 entry 都是「模型认为不属于任何已启用栏目」的赛事。如果大量出现 **已启用栏目名**（如日职联、韩K），说明改挂没生效——检查分类器是否有问题。大量出现 **非赛事**、**高中足球**、**棒球** 等正常——这些本来就不该发。

#### A3 — 降级率

```sql
-- 同期 intl 直发总量（含降级后重试为草稿的）
WITH intl_total AS (
  SELECT COUNT(*) n FROM articles
  WHERE route_league='intl' AND publish_mode_decided_at>=date('now','-14 days')
),
downgraded AS (
  SELECT COUNT(DISTINCT article_id) n FROM article_events
  WHERE event_type='RELEVANCE_DOWNGRADED' AND created_at>=date('now','-14 days')
)
SELECT intl_total.n AS intl_processed,
       downgraded.n AS downgraded,
       ROUND(CAST(downgraded.n AS REAL)/MAX(intl_total.n,1)*100,1)||'%' AS rate
FROM intl_total, downgraded;
```

> **怎么看**：降级率 10-30% 是预期范围。30%+ → 调高 `relevance_guard_min_confidence` 或检查分类器质量。

### B. 改挂效果

#### B1 — 改挂分布

```sql
SELECT DATE(e.created_at) AS d,
       json_extract(e.payload_json,'$.fallback_tab_name') AS moved_to,
       COUNT(*) n
FROM article_events e
WHERE e.event_type='LEAGUE_GUARD_UPGRADED'
  AND json_extract(e.payload_json,'$.reassigned_tab_id') IS NOT NULL
  AND e.created_at>=date('now','-14 days')
GROUP BY d, moved_to ORDER BY d, n DESC;
```

> **怎么看**：如果降级稿很少、改挂稿很多 → 说明 intl 路径大部分文章只是挂错栏目而非没价值，过滤起到了"纠偏"而非"拦截"的作用。

### C. 误杀确认

#### C1 — 抽样降级稿（人工评估）

```sql
SELECT a.id, a.title_final AS title,
       json_extract(a.quality_json,'$.league_guard.actual_competition') AS comp,
       json_extract(a.quality_json,'$.league_guard.verdict.reason') AS reason
FROM articles a
WHERE a.status='DRAFT_CREATED'
  AND json_extract(a.quality_json,'$.league_guard.downgraded_from_direct')='true'
  AND a.updated_at>=date('now','-7 days')
ORDER BY a.updated_at DESC LIMIT 30;
```

> 逐篇判断：这篇文章如果直发了，你会后悔吗？记录"Yes"的篇数和原因。

#### C2 — 低置信放行量（fail-open 的实际发生量）

```sql
-- 需要 per-article 数据：league_guard 不为空、downgraded_from_direct=false、
-- configured_publish_mode=1、effective_publish_mode=1（保持直发），且 verdict 为 false
-- 说明模型判了「不属于」但置信不足所以放行。
SELECT COUNT(*) AS fail_open_count
FROM articles
WHERE route_league='intl'
  AND json_extract(quality_json,'$.league_guard.verdict.belongs')='false'
  AND json_extract(quality_json,'$.league_guard.downgraded_from_direct')='false'
  AND json_extract(quality_json,'$.league_guard.configured_publish_mode')='1'
  AND json_extract(quality_json,'$.league_guard.effective_publish_mode')='1'
  AND updated_at>=date('now','-7 days');
```

> **怎么看**：数量应该很小（<5/天），因为分类器给出低置信 null 的概率不高。如果很大 → 分类器经常不确定，可以降低 `relevance_guard_min_confidence` 试试。

### D. 栏目标签白名单管道健康

#### D1 — 刷新审计状态

```sql
SELECT competition_id, status, season_id, team_count, player_count, total_count, error, fetched_at
FROM competition_tag_runs ORDER BY fetched_at DESC LIMIT 30;
```

> **怎么看**：所有已启用联赛的 competition_id 都应该出现，status 为 SUCCESS。REJECTED（带 error 字段）说明本周期数据骤降被保护拦住了、用的是上一版数据；连续两期 REJECTED 需要介入。FAILED 说明 StarRocks 连接失败。

#### D2 — 各 competition 标签总量

```sql
SELECT competition_id, COUNT(*) n FROM competition_channel_tags GROUP BY competition_id ORDER BY n DESC;
```

> **怎么看**：每个 competition 至少应有几百个标签。如果某个为 0 → 数据没拉进来，白名单对该栏目为空 → 按 fail-open 放行，不会删除标签，但也没有收敛效果。

#### D3 — 刷新频率确认

```sql
SELECT COUNT(DISTINCT strftime('%Y-%m-%d', fetched_at)) AS days_refreshed
FROM competition_tag_runs WHERE fetched_at>=date('now','-7 days');
```

> **怎么看**：正常应该 ≥5（每天凌晨 4:00 刷新一次）。如果是 1 → 调度没跑，标签数据停滞在初始值。

## 四、核查清单

上线 3~7 天后，逐项确认：

- [ ] **降级量在预期范围**（日均 5~25 篇，降级率 10-30%）
- [ ] **抽样 10 篇降级稿**，没有明显误杀（真正属于已启用栏目的内容被错误拦截）
- [ ] **改挂到其他栏目的文章**没有出现挂错的（如国家队 → 韩K 但内容是日职联）
- [ ] **competition_tag_runs 无 FAILED**（StarRocks 连通正常），无连续 REJECTED
- [ ] **草稿积压**没有因降级暴涨（DRAFT_CREATED 增量 ≈ 日均降级量 × 天数，可接受）
- [ ] 编辑端确认能看到降级稿的 `downgraded` 徽章和 `actual_competition` 字段

## 五、后续动作参考

| 如果… | 那么… |
|---|---|
| 降级率 <10%，误杀率 0 | 可以改 `AUTOMATIC_POST_RELEVANCE_GUARD_SCOPE=all` 扩展到所有直发路径 |
| 降级率 >30%，但没误杀 | intl 路径确实脏，不调参，编辑端也可以筛 draft 发 |
| 降级率和误杀率都高 | 调高 `relevance_guard_min_confidence`（如 0.95），或检查分类器候选栏目是否漏配 |
| 某 competition_tag 连续 REJECTED | 该联赛换了赛季/名称，StarRocks 数据未就绪，需人工排查 |
